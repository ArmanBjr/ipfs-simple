Introduction

This project is a content-addressed file storage system inspired by IPFS. Instead of storing files by name, we store them by their content hash (CID). If you upload the same file twice, it only gets stored once due to automatic deduplication.

The system has two main components: a C engine that handles the core storage operations (hashing, chunking, verification), and a Python web gateway that provides the HTTP interface and user authentication.

Architecture Overview

We split the project into two separate components that talk to each other through a Unix socket:

The Two Components

  • C Engine - Does all the real work: splits files into chunks, hashes them with BLAKE3, stores them on disk, verifies integrity, and handles parallel processing with threads
  • Python Gateway - Runs the web server, manages user sessions, and forwards requests to the engine

They communicate through /tmp/engine.sock using a custom binary protocol. We chose Unix sockets for local IPC because they have lower overhead than TCP/IP for same-host communication.

Why This Split?

We could've written everything in one language, but splitting it up has several advantages:

  • C provides better performance for CPU-intensive operations like hashing and file I/O
  • Python simplifies web development and HTTP request handling
  • The engine can be reused by other clients, not just the web gateway
  • We can restart one component without affecting the other

C Engine

The engine is written in C and handles all file storage operations, including chunking, hashing, and data persistence.

What It Does

  • Listens on a Unix socket for incoming connections
  • Splits uploaded files into 256KB chunks
  • Computes BLAKE3 hash for each chunk
  • Stores chunks in a content-addressed manner (deduplication happens automatically)
  • Creates manifest files that list all chunks for a file
  • Verifies chunk integrity during downloads
  • Handles multiple connections simultaneously using a thread pool

File Organization

The engine organizes files into three main directories:

  • blocks/ - Actual chunk data, organized as blocks/aa/bb/hash for fast lookup
  • manifests/ - JSON files that map CIDs to their chunks
  • owners/ - Tracks which user owns which file (for access control)

Key Modules

The engine code is split into logical modules:

  • engine.c - Main loop, socket handling, connection management
  • protocol.c - Binary protocol frame encoding/decoding
  • upload.c - Upload logic, streaming, chunking
  • download.c - Download logic, chunk assembly
  • blockstore.c - Chunk storage with sharding and atomic writes
  • hash.c - BLAKE3 hashing and CID generation
  • manifest.c - Manifest creation, serialization, parsing
  • threadpool.c - Thread pool for parallel chunk processing
  • locks.c - Read-write locks for thread safety
  • util.c - Helper functions (path joining, recursive mkdir, logging)

Python Gateway

The gateway is a FastAPI web application that provides the HTTP interface. It handles user authentication, HTTP requests, and forwards storage operations to the engine via socket.

Main Responsibilities

  • Serve the web interface (HTML pages)
  • Handle user authentication (signup, signin, sessions)
  • Accept file uploads from the browser
  • Forward upload/download requests to the engine via socket
  • Stream responses back to the user

Code Structure

  • main.py - FastAPI app setup, middleware, route registration
  • core/config.py - Configuration (socket path, chunk size, etc.)
  • core/engine.py - Socket client that talks to the C engine
  • core/users.py - User management, password hashing, session handling
  • routers/auth.py - Signup/signin endpoints
  • routers/files.py - Upload/download/list file endpoints
  • routers/pages.py - HTML page rendering
  • templates/ - Jinja2 HTML templates
  • static/ - CSS stylesheets

How It Works

When you upload a file through the browser, here's what happens:

  1. Browser sends file to gateway via HTTP POST
  2. Gateway reads the entire file into memory (for simplicity)
  3. Gateway opens a socket connection to the engine
  4. Sends AUTH message with your token
  5. Sends UPLOAD_START with filename and total size
  6. Splits file into chunks and sends each with UPLOAD_CHUNK
  7. Sends UPLOAD_FINISH to signal completion
  8. Waits for UPLOAD_DONE response containing the CID
  9. Redirects you to dashboard with success message

Communication Protocol

The gateway and engine communicate using a simple binary protocol. Each message is called a "frame" and has this structure: 

[1 byte opcode][4 bytes length][N bytes payload]

The length field is in big-endian format (network byte order).

Operation Codes

Opcode Name Direction Purpose
0x05 AUTH Gateway → Engine Send authentication token
0x01 UPLOAD_START Gateway → Engine Begin upload, send filename + size
0x02 UPLOAD_CHUNK Gateway → Engine Send file data chunk
0x03 UPLOAD_FINISH Gateway → Engine Signal end of upload
0x81 UPLOAD_DONE Engine → Gateway Return CID or error
0x11 DOWNLOAD_START Gateway → Engine Request download by CID
0x91 DOWNLOAD_CHUNK Engine → Gateway Send chunk data
0x92 DOWNLOAD_DONE Engine → Gateway End of download, send filename
0x30 LIST_FILES Gateway → Engine Request user's file list
0xB0 LIST_RESPONSE Engine → Gateway Return JSON array of files

Example: Upload Sequence

Gateway → Engine: [0x05][len][auth_token]
Gateway → Engine: [0x01][len][total_size + filename]
Gateway → Engine: [0x02][len][chunk_data]
Gateway → Engine: [0x02][len][chunk_data]
...
Gateway → Engine: [0x03][0][]
Engine → Gateway: [0x81][len][cid_string]

Storage & Hashing

This is where content-addressing comes into play. Instead of storing files by name, we store them by content hash.

Chunking Strategy

Files are split into 256KB chunks. This size is a good balance - small enough for parallel processing and deduplication, large enough to avoid too many small files.

BLAKE3 Hashing

We use BLAKE3 for hashing because:

  • High performance (faster than MD5, SHA-1, SHA-2, SHA-3)
  • Cryptographically secure
  • Supports parallel hashing
  • Produces 256-bit (32-byte) hashes

CID Generation

After all chunks are stored, we create a manifest JSON file that lists them. Then we hash the manifest itself to get the CID (Content Identifier). The CID format is: 

CID = multibase(base32) · multicodec(manifest) · multihash(BLAKE3(manifest))

This gives us strings like: boepcamxabvm3lbqxn2sm2hc5ejocjufanoddx3cemx7cl3deqou5upj7

Block Sharding

To avoid having millions of files in one directory (which is slow), we use a two-level sharding scheme: 

blocks/aa/bb/boepcamxabvm3lbqxn2sm2hc5ejocjufanoddx3cemx7cl3deqou5upj7

Where 'aa' and 'bb' are the first four characters of the hash. This distributes files evenly across directories.

Atomic Writes

To prevent corruption if the system crashes during a write, we use atomic writes:

  1. Write data to a temporary file: hash.tmp.12345
  2. Call fsync() to flush to disk
  3. Atomically rename to final name: rename(temp, final)

If we crash, either the old file exists or the new one does - never a half-written file.

Reference Counting

Since multiple files can share chunks (deduplication), we keep reference counts in .ref files. When a manifest is created, we increment the refcount for each chunk. When deleted, we decrement them. Only when refcount hits zero do we actually delete the chunk.

Concurrency Model

The system uses both processes and threads to handle multiple operations simultaneously.

Process-Level Concurrency

Each connection to the engine runs in its own context. The main thread accepts connections and hands them off to the thread pool. This means multiple users can upload/download at the same time without blocking each other.

Thread Pool

The engine uses a thread pool (default: number of CPU cores) to process chunks in parallel. Upload flow:

  1. Main connection thread receives chunks from gateway
  2. Each complete chunk is submitted to the thread pool as a job
  3. Worker threads hash and store chunks in parallel
  4. Results are collected in order and committed to the manifest

This allows all chunks of a file to be processed concurrently, limited only by the available CPU cores.

Thread Safety

To prevent race conditions, we use read-write locks (pthread_rwlock):

  • Blockstore lock - Protects chunk files. Multiple readers, single writer.
  • Manifest lock - Protects manifest files. Multiple readers, single writer.

We also use mutex + condition variables for the upload commit phase to ensure chunks are added to the manifest in the correct order, even though they're processed in parallel.

Authentication & Ownership

The system has two layers of authentication:

Gateway Authentication

Users sign up with username + password. The gateway stores these in data/users.json with passwords hashed using SHA-256. Sessions are managed with signed cookies.

Engine Authentication

The gateway never sends your actual password to the engine. Instead, it derives an "owner token": 

owner_token = "owner-" + SHA256(username + ":" + password)

This token is sent with every engine request. When you upload a file, the engine saves your token in owners/CID.owner. This way:

  • Only you can see your files in the file list
  • Only you can download your files (if they have an owner)
  • Only you can delete your files
  • Files without an owner are "public" (accessible to anyone who knows the CID)

Setup & Running

Prerequisites

  • Docker and Docker Compose installed
  • Or: GCC, Make, Python 3.12+ for local development

Quick Start with Docker

make up         # Build and start everything
make logs       # Watch logs from both services
make down       # Stop services (keeps data)
make reset      # Stop and delete all data

Local Development

Terminal 1 - Engine:

cd engine
make
./engine /tmp/engine.sock

Terminal 2 - Gateway:

cd gateway
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload --host 0.0.0.0 --port 8000

Then open http://localhost:8000 in your browser.

Testing

  1. Start the services: make up
  2. Open http://localhost:8000
  3. Create an account via "Sign Up"
  4. Upload a file from the dashboard
  5. Copy the returned CID and test download
  6. Upload the same file again to verify deduplication (should be instant)

Summary

This documentation covers the main aspects of the project architecture and implementation. The flow is: gateway receives HTTP requests, communicates with engine via Unix socket, engine processes chunks using worker threads, stores data by content hash, and returns CIDs.

For implementation details, refer to the source code in the repository.
